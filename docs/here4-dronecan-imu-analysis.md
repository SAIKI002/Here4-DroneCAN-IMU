# Here4 DroneCAN & IMU Analysis

## 1. Objective

This investigation examined how the **Here4 GPS module communicates with a Cube Orange+ over DroneCAN**, with a specific focus on determining whether the accelerometer and gyroscope data generated by the Here4 IMU is transmitted and consumed by ArduPilot.

The analysis covered:

- Here4 AP_Periph firmware inspection
- DroneCAN message identification
- ArduPilot DroneCAN receive-path tracing
- Runtime message logging
- Mission Planner observation
- Magnetometer-path validation
- Here4 node and firmware-update verification

The investigation deliberately separated **source-code evidence**, **observed CAN traffic**, and **unverified behavior**.

## 2. System Context

```text
Here4 GPS
   |
   |  AP_Periph firmware
   |
   +-- GPS data
   +-- Magnetometer data
   +-- IMU data (RawIMU publisher exists)
   |
   v
DroneCAN / UAVCAN
   |
   v
Cube Orange+
   |
   +-- AP_GPS_DroneCAN
   +-- AP_Compass_DroneCAN
   +-- AP_Canard_iface receive path
   |
   v
ArduPilot / Mission Planner
```

The Here4 was observed as **DroneCAN node 125**, with the node name:

```text
org.ardupilot.Here4AP
```

Mission Planner showed the node as **OPERATIONAL / OK**, confirming healthy DroneCAN communication with the node.

## 3. Here4 IMU Publisher Analysis

The Here4 AP_Periph source was examined in:

```text
Tools/AP_Periph/imu.cpp
```

The firmware was found to obtain accelerometer and gyroscope data through:

```text
imu.get_accel()
imu.get_gyro()
```

and construct a DroneCAN RawIMU message:

```text
uavcan_equipment_ahrs_RawIMU
```

The message is broadcast through the DroneCAN/Canard publishing mechanism.

### Finding

The examined Here4 AP_Periph source **contains a RawIMU publishing path for accelerometer and gyroscope data**.

This source-level finding does not by itself prove that the running Here4 firmware was transmitting RawIMU packets.

## 4. RawIMU Data Type Identification

The ArduPilot source was searched for the RawIMU data type.

The relevant definition identified:

```text
UAVCAN_EQUIPMENT_AHRS_RAWIMU_ID 1003
```

Therefore:

```text
DTID 1003 = RawIMU
```

This identifier was used when monitoring incoming DroneCAN traffic.

## 5. Searching for the ArduPilot Receiver

ArduPilot source searches were performed for:

```text
RawIMU
uavcan_equipment_ahrs_RawIMU
```

The investigation found the **RawIMU publisher** on the Here4 AP_Periph side but did not identify an obvious corresponding RawIMU subscriber in the examined ArduPilot libraries.

### Interpretation

The result suggested that the Here4 firmware may be capable of publishing RawIMU data while the examined ArduPilot software path did not show an obvious consumer for that specific message.

This is documented as an investigation finding, not as a claim that no RawIMU consumer exists anywhere in every ArduPilot configuration.

## 6. Verifying the DroneCAN Receive Path

To determine what the Cube was actually receiving, the DroneCAN receive path was traced to:

```text
libraries/AP_DroneCAN/AP_Canard_iface.cpp
```

Specifically:

```text
CanardInterface::onTransferReception(...)
```

The conceptual receive path was:

```text
CAN frame
   |
   v
Canard
   |
   v
CanardInterface::onTransferReception()
   |
   v
Message-specific handler
   |
   v
ArduPilot subsystem
```

A temporary diagnostic logger reported the source node, DTID and payload length.

## 7. Observed Here4 DroneCAN Traffic

The Here4 was repeatedly observed as:

```text
Node 125
```

Observed traffic included:

```text
N125 DTID=1001
N125 DTID=341
N125 DTID=1
```

Earlier logging also captured:

```text
N125 DTID=1063
N125 DTID=20003
```

The important result is that **Node 125 was actively transmitting DroneCAN traffic and the Cube was receiving it**.

The observed DTIDs are retained as traffic identifiers; additional sensor meanings are not assigned unless independently established in the investigation.

## 8. RawIMU Traffic Result

The expected RawIMU identifier was:

```text
DTID 1003
```

During the retained CAN-traffic monitoring:

```text
N125 DTID=1003
```

was **not observed**.

| Item | Result |
|---|---|
| RawIMU publisher exists in examined Here4 source | Confirmed |
| RawIMU DTID | 1003 |
| Here4 node detected | Confirmed |
| DroneCAN traffic from Here4 | Confirmed |
| DTID 1003 observed on monitored CAN traffic | **Not observed** |
| Accelerometer values reaching Cube | **Not verified** |
| Gyroscope values reaching Cube | **Not verified** |

## 9. Magnetometer Path Validation

Because RawIMU traffic was not observed, another Here4 sensor path was used as a control to verify that DroneCAN communication and message decoding were functioning.

The examined ArduPilot file was:

```text
libraries/AP_Compass/AP_Compass_DroneCAN.cpp
```

The magnetic-field handler was instrumented to print received values.

Mission Planner repeatedly displayed values such as:

```text
MAG1 X=-0.030 Y=-0.324 Z=-0.160
```

### Finding

This provided runtime evidence that:

```text
Here4 magnetometer
        |
        v
DroneCAN
        |
        v
Cube
        |
        v
ArduPilot compass handler
        |
        v
Mission Planner
```

was functioning.

Therefore, the missing RawIMU traffic could not simply be attributed to a completely non-functional DroneCAN connection.

## 10. IMU Thread Investigation

The AP_Periph IMU execution path was examined.

The investigation identified:

```text
AP_Periph_FW::can_imu_update()
```

and its creation through the AP_Periph scheduler as an:

```text
IMU_UPDATE
```

thread.

This established that the examined firmware contains a dedicated execution path intended to run the IMU update routine.

Additional runtime diagnostics were temporarily added around the RawIMU path:

```text
RAWIMU_TASK_STARTED
ACC ...
GYR ...
```

However, these diagnostics used `can_printf()` on the Here4 side.

### Important limitation

The absence of these `can_printf()` messages in Mission Planner **cannot be interpreted as proof that the IMU thread was not running**, because Mission Planner's Messages view primarily displays GCS messages generated on the Cube side.

Therefore, this diagnostic method did not independently establish whether the Here4 IMU thread was executing.

## 11. IMU Publishing Rate and Firmware Update Investigation

The DroneCAN node configuration exposed:

```text
IMU_SAMPLE_RATE
```

The parameter was modified as part of the investigation to determine whether the missing RawIMU traffic could be related to the publishing rate.

The Here4 node remained identifiable as:

```text
Node 125
org.ardupilot.Here4AP
OPERATIONAL
OK
```

The AP_Periph firmware was rebuilt for the Here4 target and uploaded through the DroneCAN/UAVCAN update path.

Observed node behavior included an uptime reset after the update. A software CRC change was also recorded:

```text
Old: 801E3E9FB8FEAA1E
New: 1F8F8727B8FEAA1E
```

This provides strong evidence that the modified firmware was likely reaching the Here4 node.

It does **not** by itself prove that the desired RawIMU packets were subsequently transmitted.

## 12. EKF Interpretation

An important question was:

> If Here4 RawIMU data is not observed, how is the Cube's EKF operating?

The Cube Orange+ contains its own onboard IMUs.

Therefore:

```text
Cube internal IMUs
        |
        v
     ArduPilot EKF
```

can provide accelerometer and gyroscope data independently of the Here4 IMU.

### Conclusion

Normal EKF operation **does not prove that Here4 RawIMU data is being received**.

## 13. Evidence Boundary

### Confirmed

- Here4 is detected as DroneCAN node 125.
- `org.ardupilot.Here4AP` is reported as operational.
- DroneCAN traffic from the Here4 reaches the Cube.
- GPS communication from the Here4 reaches ArduPilot.
- Magnetometer data from the Here4 reaches ArduPilot and is decoded.
- The examined Here4 AP_Periph source contains accelerometer/gyroscope acquisition.
- The examined Here4 source contains a RawIMU publisher.
- RawIMU is associated with DTID 1003.
- The AP_Periph IMU update thread exists.
- Modified firmware was likely reaching the Here4 based on node behavior and CRC changes.

### Not independently verified

- DTID 1003 appearing on the live CAN bus.
- Accelerometer values from the Here4 reaching the Cube.
- Gyroscope values from the Here4 reaching the Cube.
- Whether RawIMU publishing was disabled in the running firmware.
- Whether the running firmware differed from the examined source.
- Whether RawIMU traffic was present but missed by the monitoring method.

## 14. Working Hypotheses

The investigation identified several possible explanations for the missing DTID 1003 traffic:

1. RawIMU publishing may be disabled in the running Here4 firmware.
2. The firmware running on the Here4 may differ from the source version examined.
3. RawIMU packets may be present but not captured by the current logging method.
4. The publishing path may not be reaching the expected runtime state.

These remain hypotheses rather than confirmed root causes.

## 15. Technical Conclusion

The investigation successfully established the **DroneCAN communication path between the Here4 and Cube Orange+** and verified that at least GPS and magnetometer data were being transmitted and consumed by ArduPilot.

At the firmware level, the examined Here4 AP_Periph implementation contains an **IMU update thread and a RawIMU publishing path** using accelerometer and gyroscope data. The RawIMU message was identified as **DTID 1003**.

However, the monitored DroneCAN traffic repeatedly showed other Node 125 messages while **DTID 1003 was not observed**. Consequently, the investigation does not claim that Here4 accelerometer or gyroscope data was successfully received by the Cube.

The strongest supported conclusion is:

> **The examined Here4 firmware contains the mechanism to publish IMU data over DroneCAN, but transmission and reception of the RawIMU DTID 1003 message were not independently verified during the investigation.**

The Cube's own onboard IMUs can independently support EKF operation, so normal EKF behavior does not establish Here4 RawIMU reception.
